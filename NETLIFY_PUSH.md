# Netlify + Firebase Cloud Messaging (Spark-compatible)

This is an alternative to the previous Cloud Functions trigger. The Android sender requests a push after a Firestore notification document commits. Netlify authenticates the user and checks App Check, verifies the saved record, validates chat membership or call participants, checks blocks, restricts reward/broadcast alerts to admins and verifies vouch relationships. Pushes contain generic text, not private chat contents. Server-side Firestore transactions reserve one attempt per record and enforce sender, recipient, pair and global limits. Firebase ID tokens and App Check tokens are sent over HTTPS; FCM tokens and service-account credentials are never sent to the sender.

## Setup
1. In Netlify, import this repository (or use the existing site). Set the base directory to `server`, publish directory to `public`, and leave the build command empty. Deploy the branch containing this patch. Keep any existing World ID configuration intact.
2. In Firebase Console, choose your existing project (`uni-link-b7f2c` for this app). Project settings > Service accounts > Generate new private key if you do not already have a suitable key. In Netlify site environment variables (Functions scope), set `FIREBASE_SERVICE_ACCOUNT` to the complete JSON contents. Never put it in Git, app resources, or a chat. Prefer a dedicated service account with only the permissions needed for Firestore, Firebase Auth and FCM; if reusing the existing World ID service account, verify it has FCM send permission. Enable the Firebase Cloud Messaging API (HTTP v1) if disabled.
3. Set `FIREBASE_APP_ID` to the Android app ID (`mobilesdk_app_id` in google-services.json). App Check is enforced by default; configure Play Integrity for release and the debug provider for development. `PUSH_APP_CHECK_ENFORCE=false` is only for isolated staging, not production. Optional `PUSH_DAILY_LIMIT` defaults to 1000 attempted sends/day UTC across all users; adjust cautiously. Hosting/Firestore quotas can be exhausted before this limit. Redeploy after changing environment variables.
4. Run `cd server && npm ci && npm test`, then return to the repo root. Review current production Firestore rules and test in staging before deployment. Run `firebase use` and `firebase deploy --only firestore:rules`. **Do not deploy Firebase Functions.** The old code is retained as reference but removed from firebase.json. If the previous trigger was deployed, disable it separately before rolling out this backend to avoid duplicates.
5. Copy the actual Netlify HTTPS origin into `app/src/main/res/values/push_backend.xml` (e.g. https://your-site.netlify.app). It is intentionally blank until the owner supplies the correct URL. Do not use the Firebase Hosting URL unless you explicitly proxy /api/sendPush there. Build and install the updated APK on both sender and receiver. Both users need verified accounts; open the app on each phone to register its private device token and grant notifications.
6. Verify the route without credentials: `curl -i -X POST https://YOUR-SITE.netlify.app/api/sendPush -H 'Content-Type: application/json' -d '{}'` should return HTTP 401 (not 404 or 503). Test one-to-one and group chat, call, blocked users, account switching, locked screen and swipe from recents. Check Netlify function logs and Android Logcat tag NetlifyPush. A 429 indicates a rate limit. Force stop in Android Settings blocks FCM until reopened.

## Limits and tradeoffs
This is a best-effort sender-triggered delivery path. If the sender goes offline or closes before making the HTTP call, the inbox record survives but push may be missed. A failed reserved FCM send is not automatically replayed (at-most-one attempt, not exactly-once delivery). The existing client stores a single active token per account; no multi-device fanout. Admin broadcasts use the existing batch and bounded client queue, so large broadcasts may be partial. Vouch notifications depend on the source write completing first. Existing client-writable chat membership/call signaling remain broader security concerns: checks limit this endpoint but do not prove all underlying social events are genuine. Unauthenticated requests still consume hosting invocations; use platform controls for further protection. Rate counters are server-only and update fixed UTC windows, not rolling windows. Review Netlify and Spark quotas; free hosting is not unlimited. No paid Google Cloud Functions deployment is needed for this path. Netlify deployments, Firestore rules compilation, Android compilation and device delivery must be verified by the project owner.
